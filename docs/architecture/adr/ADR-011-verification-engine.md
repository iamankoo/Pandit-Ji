# ADR-011: The verification engine (`services/verification`, package `pandit_verification`)

Status: Implemented 2026-10-05 (Phase 16), within existing locked decisions (ADR-006, ADR-010 owner decisions of 2026-10-03, `Phases.md` Phase 16). It adds no canonical service. It raises no new owner decision; the judgement calls it made are listed under "Decisions" so the owner can confirm or change them.

## Context
`Phases.md` Phase 16 asks for: calculation verification, rule verification, evidence tracking, contradiction detection, hallucination detection, unsupported-claim detection, and confidence/uncertainty representation; deliverable: a verified-response pipeline (AI answer, verifier, approve or regenerate). ADR-006 makes verification an independent layer with direct access to the evidence bundle the agent used and the draft itself. ADR-010 (owner-locked) makes Phase 15 responsible for structure and reference integrity only and makes Phase 16 the only phase that may set `VERIFIED`.

## Decisions
1. **Location and independence.** `pandit_verification` inside the existing `verification` service. It depends on `pandit-contracts` and `pandit-shared` only. It does not import the agent, a model, a network client or the calculation packages (a test checks the imports). It reads the Phase 6 `EvidenceBundle` structurally, as the agent does.
2. **The verifier resolves trusted evidence itself.** It is handed the bundles (`PalmEvidenceBundle`, Phase 6 `EvidenceBundle`), not the agent's `EvidenceRecord` objects and not anything inside the narration. It re-hashes each bundle (the palm bundle with `bundle_hash_of`, the astrology bundle with the Phase 6 hashing rule) and an optional, injected independent recomputation (palm rule re-evaluation; astrology re-evaluation) can be required to reproduce the bundle. An inconsistent bundle makes every claim on it `INVALID_REFERENCE`. The contracts' own `EvidenceReference` and `EvidenceRecord` types are reused; no parallel evidence model exists.
3. **Verification contract** (`pandit_contracts.verification`, additive; `agent.py` is unchanged). Seven statuses: `VERIFIED`, `UNSUPPORTED`, `UNVERIFIABLE`, `INVALID_REFERENCE`, `CONFLICTING_EVIDENCE`, `POLICY_BLOCKED`, `INSUFFICIENT_EVIDENCE`. Neither `Phases.md` nor an existing contract defined these, so they were introduced here; `VerificationState` (`UNVERIFIED` / `VERIFIED`) is kept as the claim-level flag the agent contract already had. Results carry reason codes, resolved provenance, computed uncertainty, hashes and versions, never claim text.
4. **Precedence of one status per claim:** `POLICY_BLOCKED`, `INVALID_REFERENCE`, `CONFLICTING_EVIDENCE`, `INSUFFICIENT_EVIDENCE`, `UNSUPPORTED`, `UNVERIFIABLE`. All reasons found are kept in the result.
5. **Semantic grounding is closed-vocabulary lexical grounding.** The text analyzer (`text.py`) recognises a fixed set of entities (planets, signs, house numbers, dignity, retrograde, hand sides, palm lines and mounts, life topics, valence words, certainty words, framing words, observation and derivation wording) and the engine checks what it recognised against the trusted evidence. It proves that recognised assertions match the evidence and that nothing it can recognise goes beyond the evidence. It does not prove arbitrary prose and does not claim to; text it cannot read is `UNVERIFIABLE`. No LLM is used in verification (the roadmap does not call for one, and ADR-006 says verification is not a second LLM call with a vague prompt).
6. **Claim-type behaviour.** Fact claims (`CALCULATION_FACT`, `OBSERVED_FEATURE`, `DERIVED_FEATURE`) must cite facts of the matching semantic class, carry no outcome wording, no life topic and no valence, and have at least one recognised, grounded entity. `TRADITIONAL_INTERPRETATION` must rest on at least one `TRIGGERED` rule, be framed as a tradition's reading, reflect at least one cited tag, mention only topics the cited tags carry, and not contradict the rule's effect class. `LIMITATION` is verified only when the cited evidence actually shows the gap (not evaluable, not triggered, not visible, conflicted, unresolved dependency) or, without a reference, when a trusted record of the missing capability is supplied.
7. **Source conflicts are preserved.** Rules from different sources that share a conflict group are never merged into one claim (`CONFLICTING_EVIDENCE`). A single conflicted rule can be verified only when the claim names its source (author or work); the conflict stays visible in the result's uncertainty (`CONFLICTING_PROFILES`). A claim built on rules from several non-conflicting sources is `UNVERIFIABLE` (it cannot be attributed to one source) because the repository has no source-policy rule for merging profiles.
8. **Uncertainty is enforced, not manufactured.** Non-evaluable, non-visible, missing-basis and below-floor evidence cannot yield `VERIFIED`. The verifier invents no confidence floor (Phase 13 confidences are uncalibrated); `min_confidence_bp`, `require_calibrated_confidence` and `require_production_ready` are explicit configuration. By default an uncalibrated or not-production-ready bundle can still verify a claim, and the result then carries the flags `UNCALIBRATED_CONFIDENCE` and `BUNDLE_NOT_PRODUCTION_READY`. So `VERIFIED` means supported by the encoded evidence, not production-grade.
9. **Safety.** The verification policy is its own copy of the agent's domain scoping (palmistry: every Phase 13 category; astrology: lifespan plus death timing), the Hindi and Hinglish supplement, injection, forged-authority, embedded-evidence and claimed-verification patterns. A repository test asserts the supplement and the restricted categories equal the agent's, so the copies cannot drift. A blocked claim is never evaluated further.
10. **Release decision (`Approve / Regenerate`).** `APPROVE` when every claim is `VERIFIED`; `RELEASE_VERIFIED_ONLY` when at least one is `VERIFIED` and the rest are only `UNVERIFIABLE` or `INSUFFICIENT_EVIDENCE`; `REGENERATE` when nothing is verified or any claim is wrong, blocked or invalid; `NOTHING_TO_VERIFY` for a refusal or an empty narration. Mixed results are always reported claim by claim. The roadmap does not require all-or-nothing, and a claim that is merely unreadable or under-evidenced does not discard the others. A wrong, blocked or invalid claim triggers `REGENERATE` because releasing the rest next to a hallucination is not safe by default. This is the verifier's recommendation; the loop that regenerates belongs to the orchestration that composes the services (Phase 18), not to the verifier.
11. **`VERIFIED` is set in one place.** `pipeline.apply_report` marks a claim `VERIFIED` and sets `verified_by` only for claims the verifier returned as `VERIFIED`, on a copy. An input claim or response that already carries `VERIFIED` or a `verified_by` is treated as forged (`POLICY_BLOCKED`, `input_forgery_detected`, `REGENERATE`). `verified_by` is a label (`pandit-verification@<version>`), not a signature; consumers must trust the `VerificationResponse` (its `report_hash` and trace), not a string on a claim. A signed attestation belongs to the API boundary (Phase 18).
12. **Determinism.** No clock, randomness, network or model. Identical claims, evidence, configuration and verifier version give an identical result and `report_hash`. There is deliberately no wall-clock timestamp in a result; a caller that wants one records it outside the hashed report.

## Research
No external research was needed or done for the methodology: the roadmap fixes it (deterministic checks against the evidence bundle, ADR-006), and the project rule is to return `UNVERIFIABLE` rather than invent a verification mechanism where the repository cannot support one. The decisions above are engineering choices inside that frame; none is a claim about astrology or palmistry being valid. OWASP LLM01 (prompt injection), already cited by ADR-010, informs the treatment of narration as untrusted input (typed channels, no authority fields, adversarial tests), and, as there, prevention is not claimed to be fool-proof.

## Consequences
- The agent's narration can now be judged against the real bundles with a typed, auditable per-claim result and a release recommendation.
- Known limits (not hidden): the analyzer is English first with a small Hindi and Hinglish vocabulary (`CALIBRATION_REQUIRED`); it cannot judge prose outside its vocabulary; an interpretation is checked against the rule's tags, effect class, source and status, not against the source's full wording; the astrology rule's reading conditions are not re-derived (the optional recomputation hook is the independent check, and independent recalculation from birth data is not done because the verifier is deliberately given no birth data); multi-profile claims from non-conflicting sources are `UNVERIFIABLE`; a regenerate loop, persistence of verification results, a signed attestation and an HTTP surface are not built (Phase 18).
